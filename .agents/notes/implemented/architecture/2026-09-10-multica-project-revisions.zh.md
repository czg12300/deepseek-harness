# Agent Note: Multica 项目版本由项目数据库管理

Status: implemented

[English](2026-09-10-multica-project-revisions.md) | 中文

## 问题

创作者需要在不依赖 agent（智能体）对话的情况下重新打开项目规格、大纲和单集草稿。否则，并发编辑者可能覆盖彼此的工作，恢复旧内容也可能抹去理解后续制作结果所需的证据。

## 决定

Multica 在 SQLite 中为每个项目保存稳定身份和不可变的聚合版本。每个版本包含项目规格、大纲和单集草稿。保存时在写入事务内比较调用者的预期版本。冲突会返回当前项目且不执行写入；浏览器保留本地草稿供用户合并。归档状态随版本保存，由宿主服务执行约束。恢复历史内容会创建新版本。

[项目服务](../../../../packages/multica/studio-core/README.zh.md)负责数据库并公开类型化 Remote 操作。[浏览器工作台](../../../../packages/client/ui-multica/README.zh.md)通过现有插槽注册表提供全局主面板和左侧栏“漫剧”入口。Web profile 通过常规 bundle 挂载两者。创建、打开和编辑项目不会创建 Session 或发起模型请求。

项目数据与 Session 数据分别保有自己的权威来源。后续 agent 集成必须将实际进入模型请求的项目快照记入对应 Session；回放时读取数据库最新内容不能重建模型当时看到的信息。现有[模型可见内容记录规则](../../../../docs/architecture.zh.md)仍是权威要求。

## 考虑过的替代方案

**仅存储在浏览器。** 这不能让宿主权威地约束归档状态和并发保存，浏览器来源变化也可能导致已保存工作无法访问。SQLite 提供独立于浏览器的持久化事务。

**从对话推导项目。** 项目在首次对话前就已存在，也可由用户手动编辑。若让对话历史管理这些独立编辑，普通项目管理就必须人为创建模型工作。

**为所有未来制作对象分别建立版本表。** 资产、审批和生成任务在对应能力启用时需要独立身份。项目基础版只有规格和文本草稿，因此使用一次聚合保存即可保证原子性，无需实现尚未验证的后续阶段关系。

目录可携带性与项目内 Session 存储位置由[可携带项目决策](2026-09-17-portable-multica-projects.zh.md)负责。

## 影响

聚合版本的存储开销与项目文本规模成正比，两位编辑者修改不同集时也会发生冲突。它为首版本地工作台提供一致的恢复点，并使历史记录独立于浏览器状态。大型制作资产和更细粒度编辑需要在媒体制作启用前建立各自的版本管理。

基础版不挂载专业 agent，不公开付费制作操作，并明确显示助手不可用。这里的项目隔离用于分离存储记录，不提供多用户授权系统。
